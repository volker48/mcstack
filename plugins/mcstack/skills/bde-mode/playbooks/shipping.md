### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge, then verify each PR independently before it lands.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One verifier per PR, each a background Agent with `isolation: "worktree"`, runs the change the way a user would with the matching control skill (the project's `verify-*` skill, browser tools for UIs, or Bash for CLIs), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.

   Check the review bots the same way, because a bot's silence covers only the commits it reviewed. Bots such as CodeRabbit (`coderabbitai`) and Codex (`chatgpt-codex-connector`) skip commits once they hit a rate limit, and Codex reviews on its own only when the PR opens or leaves draft. Before you merge, compare the commit each bot last reviewed with the PR's head. On GitHub, run `scripts/review-coverage/review-coverage <pr>` (`--repo <owner/name>` outside the checkout). It reads each bot's own records: its reviews, Codex's state comment, which is the only record of a pass that found nothing, CodeRabbit's summary, and cubic's check run. It prints the head and one line per bot that left a record, saying whether that bot covered the head and, when it did not, which commits it reviewed and why it stopped, such as a review limit. It exits 0 when every listed bot covered or summarized the head, 1 when one missed it or no bot left a record, and 2 when it could not run, which leaves the head unchecked. A bot that left no record is named on its last line and has reviewed nothing. A bot that `summarized` the head, such as CodeRabbit on its Free plan, wrote a summary and never looked for findings, so exit 0 does not mean it reviewed the head: report it as a summary, not as a review that found nothing. The script compares exact commits. A head whose `git patch-id` matches a reviewed commit's also counts as reviewed, but the script still reports it missed, so check that by hand. When a bot did not cover the head, comment `@codex review` or `@coderabbitai review` and wait for that pass, or name the unreviewed commits in the reply. Never report that a bot found nothing in a commit it did not review. The script is GitHub's. On Origin, read each bot's reviews and summary comments for the same facts if `origin pr view` shows them, and otherwise say in the reply that bot coverage of the head was not checked.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `origin pr merge <pr>` or `gh pr merge <pr> --squash`. On Origin the plain command also merges every PR below the one you name, and on GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`origin pr view <pr>` or `gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `--auto` (Origin merge-when-ready or GitHub auto-merge) only on a PR whose verdict covers its current head, because it lands whatever head is ready. After a merge lands, retarget the PR whose base was the merged branch to trunk (`origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass, its verdict survives, and step 3's review-bot check has run on its new head.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. On GitHub, watch the run with the queued watcher from `playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`) under `/loop` until it reports `COMPLETE` at the ceiling. On Origin, re-read the current PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, the commit each review bot reviewed and any head it missed, what landed and how you confirmed it, and what the next gap needs.
